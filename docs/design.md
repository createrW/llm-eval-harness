## 1. Intent

An open-source harness that evaluates small LLMs on benchmark tasks and reports results the way a
statistician would: every accuracy carries a bootstrap 95% confidence interval and an `n`; every
model-vs-model or prompt-vs-prompt claim is a *paired* test on the same examples, corrected for the
number of comparisons made under a pre-specified decision rule; the variance in scores is decomposed
into model, prompt, interaction and item-difficulty shares; and every number is reproducible from
`(config, seed, code sha, model revision, dataset revision)`.

The gap it fills: typical "LLM eval" portfolio projects print a point estimate per model and call
the higher one better. With 300–500 examples, a 2–3 point gap is usually inside the noise. This
project is a showcase for Microsoft Applied Scientist / GE Vernova AI Evaluation / Mercor Research
Scientist style roles, so the statistical protocol *is* the product; the models and tasks are
deliberately small so the whole grid runs on a laptop.

## 2. Goals, non-goals, anti-goals

**Goals (from the brief)**

1. Config-driven runs: one YAML declares `models × tasks × prompt_variants`, `n_examples`, `seed`.
2. Local models via Hugging Face transformers: `Qwen/Qwen2.5-0.5B`, `meta-llama/Llama-3.2-1B`.
3. Optional API models: GPT-4o-mini (OpenAI), Claude Haiku (Anthropic). Keys only from env vars.
4. Tasks: HellaSwag (validation subset, n=500 final / n=100 Day 1) and GSM8K (test subset, n=300).
5. Prompt variants per task: `zero_shot`, `few_shot_3`, `cot`.
6. Metric: accuracy with bootstrap 95% CI (1000 resamples, seeded) — from Day 1, never a bare point estimate.
7. Pairwise significance: Wilcoxon signed-rank (as specified) reported next to McNemar exact (the
   primary test, §7.7) and a paired bootstrap of the difference, Bonferroni-corrected (Holm also shown).
8. Reports: per-model table, per-prompt table, pairwise significance matrix, variance decomposition.
9. Streamlit dashboard: pick any two cells of the model×prompt grid → paired per-example analysis.
10. README that leads with a forest plot of paired differences with CIs and one generated sentence of
    the form "a point-estimate leaderboard orders all K pairs; M survive the pre-specified paired test;
    the top cell is #1 in Z% of bootstrap resamples", then the experiment protocol (named hypotheses →
    metrics → decision rule → minimum detectable effect), the measured test–retest numbers (§7.5),
    example tables generated by `llm-eval report`, and how to add a task / model.

**Non-goals (from the brief)**: rich UI, LLM-as-judge (optional stretch), multi-GPU inference,
fine-tuning, leaderboard parity with lm-evaluation-harness (we follow its HellaSwag formatting and
scoring so numbers are comparable, but parity is not a goal).

**Anti-goals** (what would make this a failure even if it "works"):

- A reported accuracy without an interval and an `n`.
- A "model A beats model B" claim from unpaired comparisons, without multiple-comparison correction,
  or with the test chosen after seeing the data.
- Hidden nondeterminism: a rerun with the same config that cannot be compared example-by-example.
- Secrets or large artifacts in git (model weights, raw datasets, API keys).
- A dashboard that is prettier than it is correct.

## 3. Constraints

- **Stack is fixed**: Python 3.11, PyTorch + transformers (local inference), OpenAI + Anthropic
  SDKs (optional extra), statsmodels + scipy (statistics), Streamlit (dashboard), MLflow self-hosted
  file store (tracking), pytest. One addition flagged for the user: `matplotlib` in an optional
  `report` extra, only to render the README forest plot to PNG.
- **Packaging**: `uv` with a committed `uv.lock`. Core `dependencies` are torch-free (pydantic,
  pyyaml, pandas, pyarrow, numpy, scipy, statsmodels, tqdm). Local inference is the `local` extra
  (`torch`, `transformers>=5,<6`, `datasets`, `huggingface-hub`); `api`, `dashboard`, `tracking`,
  `report` are the other extras; `all` = every extra. On Linux, torch resolves from the PyTorch CPU
  index (`[tool.uv.sources]`) so CI and the Docker image stay small; a CUDA box runs
  `uv pip install --torch-backend=auto torch` after `uv sync`. Two generated files, never hand-edited
  (`make requirements`): `requirements.txt` = core + `dashboard` extra + `-e .` (what Streamlit
  Community Cloud installs; contains no torch) and `requirements-local.txt` = core + `local` + `report`
  with the CPU index URL emitted (for pip users running evals).
- **Layout** follows `code_standard.md` (§4). The package root is `src/llm_eval/` as the brief
  requires; the standard's sub-package taxonomy (`data/ models/ features/ evaluation/ serving/`)
  lives inside it.
- **Dev machine**: Apple M5, 16 GB unified memory, no CUDA. Everything must run on `mps` and on
  `cpu` (CI) and, unchanged, on a Linux CUDA box (rented GPU for the full grid). Measured
  2026-10-18: Qwen2.5-0.5B fp32 weights 1.9 GB; peak MPS driver memory ≈3.7 GB at batch 8 / 80
  tokens, ≈7.7 GB across an n=500 run; load ≈4 s; n=100 × 4 endings scoring ≈35 s at batch 8 on MPS,
  ≈3 min on CPU.
- **Secrets**: `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `HF_TOKEN` (Llama is gated) come from the
  environment only. Configs never contain keys.
- **Git**: repo is created and pushed by the user. The tree must be push-ready at the end of every
  day: `.gitignore` excludes data/runs/venv/mlruns; `data/samples/` holds committed runs (§8.3) so
  tests and the dashboard work from a fresh clone with no downloads.
- **Time**: 7 days, one engineer. Day 1 scope is §11 "Day 1".

## 5. Architecture

```mermaid
flowchart LR
    Y[YAML config] --> C[config.py<br/>pydantic EvalConfig]
    C --> G[expand_grid: GridCell list<br/>model × task × variant × resolved scoring]
    G --> R[runner.py]
    R --> T[data/*Task<br/>load + preprocess + nested subset]
    R --> P[features/prompts.py<br/>render variant]
    R --> M[models/*<br/>loglikelihood | generate]
    T --> P --> M --> S[evaluation/metrics.py<br/>score per example]
    S --> W[evaluation/results.py<br/>examples.parquet + run.json]
    W --> ST[evaluation/stats.py<br/>shared bootstrap · paired tests · decision rule]
    W --> V[evaluation/variance.py]
    ST --> RP[report.py tables + leaderboard sentence]
    V --> RP
    W --> D[serving/app.py Streamlit]
    RP --> ML[tracking.py MLflow]
```

Design rules:

- **Records are the contract.** Everything downstream (stats, dashboard, MLflow) consumes the
  long-format per-example table from §8.2, written with an explicit pyarrow schema. Day 1 must get
  this schema right because Days 4–6 only read it; the schema already carries the columns Days 2–3
  fill (`generation`, `parse_ok`, `exemplar_ids`, `status`, `error`).
- **Tasks know text, models know tokens, variants know layout.** A task converts a raw dataset row
  into a fully preprocessed `Example` (its `choices` and `target` are authoritative), renders its
  `context`, and judges a prediction. A model adapter scores `(context, continuation)` pairs or
  generates text. A prompt variant decides how exemplars / instructions wrap the task text, calling
  only public `Task` methods (`context`, `target_text`). None of the three imports the others' internals.
- **Two scoring modes.** `loglikelihood` (multiple choice; local models only) and `generation`
  (free text; all models). The capability matrix is in §7.4; the resolved mode and the resulting
  `metric` are columns, and statistics never pool rows with different `metric` (§7.6).
- **Registries, not if-chains.** `data.dataset.TASKS` is populated by `@register_task` and
  `data/__init__.py` imports every task module, so `import llm_eval.data` registers all tasks.
  `models.registry.PROVIDERS` maps a provider string to a factory + static capabilities via
  `@register_provider`; each factory imports its heavy module inside its body. "Add a task" = one
  file + one decorator; "add a provider" = one file + one decorator.
- **Import rule.** `torch`/`transformers` are imported only in `models/hf_model.py`; `datasets`
  only inside `Task` method bodies; `serving/` imports only `evaluation.*`. `tests/test_imports.py`
  asserts that `import llm_eval.config, llm_eval.evaluation.results, llm_eval.evaluation.report`
  leaves `torch` and `datasets` out of `sys.modules`.
- **Every random draw comes from `seeding.child_rng(seed, *keys)`**, which builds
  `numpy.random.default_rng(SeedSequence([seed, stable_hash(k) for k in keys]))` with
  `stable_hash(s) = int.from_bytes(sha256(s.encode()).digest()[:8], "big")`. Python's salted
  `hash()` is never used. Independent streams (subset, exemplars, bootstrap) therefore never
  depend on evaluation order.

## 6. Core abstractions (names and signatures are binding for the plan)

```python
# src/llm_eval/data/dataset.py
class TaskType(str, Enum): MULTIPLE_CHOICE = "multiple_choice"; GENERATION = "generation"

@dataclass(frozen=True)
class Example:
    id: str                   # f"{task}/{split}/{row_idx}", row_idx = 0-based row position in the HF split at the
                              # pinned dataset_revision. HellaSwag `ind` is NOT unique (9,609 distinct over 10,042
                              # validation rows; 433 duplicated values) and is kept in `inputs` for traceability only.
    inputs: dict[str, Any]    # task-native fields after preprocessing
    target: str               # canonical gold: MC → choice index as str ("2"); generation tasks → canonical answer ("42")
    choices: tuple[str, ...] | None = None   # MC only; preprocessed endings, authoritative (gold index = int(target));
                                             # may begin with a space after `[substeps]` removal — lm-eval parity

class Task(ABC):
    name: ClassVar[str]; task_type: ClassVar[TaskType]
    dataset_path: ClassVar[str]; dataset_revision: ClassVar[str]   # HF repo id + pinned commit sha
    default_split: ClassVar[str]
    stop_sequences: ClassVar[tuple[str, ...]] = ()                 # generation mode; HellaSwag ("\n\n",), GSM8K ("\n\nQuestion:",)
    def __init__(self, rows: Callable[[str], Sequence[Mapping[str, Any]]] | None = None)   # test seam: rows(split) replaces load_dataset
    def load(self, split: str, n_examples: int | None, seed: int) -> list[Example]   # §7.5 nested-subset rule; raises if n > len(split) or ids collide
    def dataset_info(self) -> dict[str, Any]   # {"path","revision","split","n_rows"}; valid after load
    @abstractmethod
    def context(self, example: Example) -> str # rendered question/context, no exemplars, no trailing whitespace
    def is_correct(self, prediction: str | None, example: Example) -> bool   # default: prediction == target
    # Day 2
    def target_text(self, example: Example) -> str        # gold continuation as shown in a few-shot exemplar (HellaSwag: choices[int(target)];
                                                          # GSM8K: full rationale with "#### N" rewritten to "The answer is N.")
    def exemplars(self, k: int, seed: int, example_id: str) -> list[Example]   # per-example draw, §7.3
    def extract_answer(self, generation: str) -> str | None                     # None = unparsable

TASKS: dict[str, type[Task]];  def register_task(cls) -> cls;  def get_task(name: str) -> Task
```

## 7. Evaluation methodology

### 7.1 HellaSwag (multiple choice, log-likelihood)

Dataset `Rowan/hellaswag` (HF, ungated, parquet-only), pinned `dataset_revision =
218ec52e09a7e7462a5400043bb9a69a41d06b76`, fields `ind, activity_label, ctx_a, ctx_b, ctx,
endings[4], label (str), split, split_type, source_id`. We use the **validation** split
(10,042 rows; `test` has no labels). `Example.id = f"hellaswag/validation/{row_idx}"` (§6).

Preprocessing follows lm-evaluation-harness exactly so our numbers are comparable to published ones:

```python
def _preprocess(text: str) -> str:
    text = text.strip()
    text = text.replace(" [title]", ". ")        # WikiHow artefacts
    text = re.sub(r"\[.*?\]", "", text)
    return text.replace("  ", " ")

ctx     = row["ctx_a"] + " " + row["ctx_b"].capitalize()
context = _preprocess(row["activity_label"] + ": " + ctx)
choices = tuple(_preprocess(e) for e in row["endings"])   # ≈27% begin with a space (from "[substeps] …"); kept — parity
target  = str(int(row["label"]))
```

Scoring: for each choice `c_i`, `ll_i = Σ log p(tokens of " " + c_i | context)` (continuation gets a
leading space, context does not get a trailing one; a choice that already begins with a space
therefore yields two spaces, as in lm-eval). `pred = argmax ll_i` → **acc**.
`pred_norm = argmax ll_i / len(c_i)` → **acc_norm**, where `len(c_i)` is the *character* length of
the preprocessed choice without the delimiter — identical to lm-eval `acc_norm`. (A worked flip that
a unit test pins: `ll = (-5, -20)`, `len = (10, 41)` → `-0.500` vs `-0.488` → `pred_norm = 1`; the
old "+1 byte" denominator would have picked 0.) Both are stored per example; for log-likelihood MC
cells the primary metric is `acc_norm` (§7.6).

**Tokenization contract** (lm-eval `_encode_pair` semantics, implemented in `HFCausalLM`):
```python
n_sp = len(context) - len(context.rstrip())           # trailing spaces move to the continuation
if n_sp: continuation = context[-n_sp:] + continuation; context = context[:-n_sp]
whole_ids = tok(context + continuation, add_special_tokens=True).input_ids   # BOS iff the tokenizer adds one (Llama-3 yes, Qwen2.5 no)
n_ctx     = len(tok(context, add_special_tokens=True).input_ids)
cont_ids  = whole_ids[n_ctx:]                          # never encode the continuation on its own
```
Only `cont_ids` positions are scored; `n_tokens = len(cont_ids)`, `n_context_tokens = n_ctx`.
`len(cont_ids) == 0` or `n_ctx == 0` raises. Inputs longer than `model_max_length` drop tokens from
the left of the context only (keeping BOS), never from the continuation. Verified 2026-10-18 on
all 40,168 HellaSwag validation pairs with the Qwen2.5 tokenizer: the context prefix is preserved
and the slice equals the separately encoded continuation.

**Batching contract**: pad id = `tokenizer.pad_token_id`, else `eos_token_id` (Qwen2.5:
pad == eos == 151643; Llama-3.2 ships no pad token). Right padding; the attention mask is built
from per-row lengths, never from `ids != pad_id`. Logits are sliced to each row's continuation
positions *before* `log_softmax`; `[B, L, V]` log-probs are never materialised or copied to CPU.
Requests are sorted by length; default `batch_size` 8. Batched and unbatched scores agree to 1e-4
on the tiny test model (observed 7e-8) and the slow real-model test asserts identical predictions
and |Δll| ≤ 1e-3 (observed 8.8e-5 on MPS fp32).

Sanity anchors (approximate, from public leaderboards and a reference run on 2026-10-18; used only to
catch pipeline bugs): Qwen2.5-0.5B zero-shot `acc_norm` ≈ 0.45–0.60 and `acc` ≈ 0.38–0.48;
Llama-3.2-1B `acc_norm` ≈ 0.60–0.66. At n=100 the 95% CI half-width is about ±0.10, so the Day 1
smoke run validates the pipeline, not the model.

### 7.2 GSM8K (generation, exact match) — Day 2

Dataset `openai/gsm8k` config `main`, split `test`, n=300, pinned revision recorded in the task
class. Target is the number after `####` in the answer field. Prediction = the number after
`The answer is` if present, else the last number in the generation, compared after stripping
commas, `$`, trailing `.`, and normalising `3.0 == 3`. Unparsable → `extract_answer` returns
`None`, `parse_ok=False`, `prediction=""`, `correct=False` (a model failure stays in the analysis).
Greedy decoding, `max_new_tokens = MAX_NEW_TOKENS[variant]` (256 / 256 / 512), optionally capped by
`ModelConfig.max_new_tokens`; stop on `"\n\nQuestion:"`. Truncation rate (generations that hit the
cap) is reported per cell.

### 7.3 Prompt variants

| variant | HellaSwag, log-likelihood mode (hf) | HellaSwag, generation mode (API, or `scoring: generation`) | GSM8K (generation) |
|---|---|---|---|
| `zero_shot` | `context` → score 4 continuations | `context\nA. c0\nB. c1\nC. c2\nD. c3\nAnswer:` → first `[A-D]` letter | `Question: q\nAnswer:` → extract number |
| `few_shot_3` | 3 exemplars rendered as `context(ex) + " " + target_text(ex)`, joined by `\n\n`, then the query | 3 exemplars in the lettered format ending `Answer: B`, joined by `\n\n`, then the query | 3 `Question:/Answer:` exemplars with full solutions ending `The answer is N.`, then the query |
| `cot` | — (generation mode only) | lettered block, then `Answer: Let's think step by step.` → generate → last standalone `[A-D]` (prefer `answer is (X)`) | `Question: q\nAnswer: Let's think step by step.` → extract number |

`features/prompts.py` renders exemplars only through `task.context()` and `task.target_text()`.
`GenerationRequest.stop` comes from `task.stop_sequences`.

**Exemplars** are drawn *per example* from the task's train split with
`child_rng(exemplar_seed, "exemplars", task.name, example.id)` (`exemplar_seed` defaults to
`seed`), sampled without replacement from a pool that never contains evaluation ids. The draw
depends only on `(exemplar_seed, example_id)`, so it is identical for every model in the run
(pairing preserved) and independent across examples; the example bootstrap and the paired tests
therefore cover exemplar variability, and "few-shot helps" is a claim about the exemplar
distribution, not one lucky set. The ids are stored per row (`exemplar_ids`). Varying
`exemplar_seed` with `seed` fixed measures exemplar sensitivity on identical example ids (§7.5).

**HellaSwag `cot` and the scoring confound.** `cot` requires generation, so on HellaSwag the
prompt factor would be confounded with the scoring mode (and a 0.5B base model asked to emit a
letter will often fail — that is reported, not hidden). The design therefore runs two HellaSwag
analyses: the **model comparison** in log-likelihood mode over `zero_shot`/`few_shot_3` (headline,
metric `acc_norm`), and the **prompt-effect analysis** in generation mode for all three variants
(`configs/eval/hellaswag_prompt_effects.yaml`, `scoring: generation`, metric `acc`), which is the
only apples-to-apples prompt comparison. Cells from different modes never share a test or an ANOVA.

### 7.4 Scoring-mode capability matrix

| | hf × zero/few-shot MC | hf × cot MC | hf × GSM8K | openai / anthropic |
|---|---|---|---|---|
| `loglikelihood` | ✅ default | ✗ | ✗ | ✗ (no prompt logprobs) |
| `generation` | ✅ if forced (`scoring: generation`) | ✅ | ✅ | ✅ |

`expand_grid` resolves `scoring: auto` per cell to `loglikelihood` when the provider's
`ProviderSpec.supports_loglikelihood` is true and the cell is a non-cot MC task, else `generation`.
It then rejects, before any model loads and naming the offending cell: any cell not in `SUPPORTED`
("lands on Day N" from `LANDS_ON_DAY`); an explicit `loglikelihood` cell that is `cot`, a
GENERATION task, or on a provider without log-likelihood. The resolved mode and the `metric` are
columns in the results (§8.2), so cross-mode numbers are never silently mixed in a table or a test.

### 7.5 Determinism and provenance

- **Subset selection**: `perm = child_rng(seed, "subset", task.name).permutation(n_rows)`;
  `idx = sorted(int(i) for i in perm[:n])` (`n_examples=None` on the task → inherit the config
  value). Subsets with the same seed are **nested** (n=8 ⊂ n=100 ⊂ n=500), so smoke runs, test
  fixtures and `--n-examples` overrides can be paired with the final grid on `example_id`.
  `n > n_rows` is an error raised before any model loads. `run.json["tasks"][name]["example_ids"]`
  stores the `Example.id`s in subset order, so a rerun is verifiable without trusting the RNG.
- **Decoding**: greedy, no sampling anywhere; `torch.manual_seed(seed)` before model load
  (defensive — nothing in eval is stochastic).
- **Numerics**: `dtype: auto` = `float32` on every device (cuda, mps, cpu). Half precision is
  opt-in per model and recorded; a cell run in another dtype is a different condition, not a rerun.
  Measured 2026-10-18 (Qwen2.5-0.5B, 100 HellaSwag examples): bf16 vs fp32 max |Δ loglik| = 0.69
  nats with 1/100 prediction flips; fp32 CPU vs MPS max |Δ| = 7.7e-3 with 0 flips; two fp32 MPS
  reruns were bitwise identical. The adapter **always passes an explicit `dtype=<torch.dtype>`** to
  `from_pretrained` and never forwards the string `"auto"` or omits the kwarg: in transformers 5 both
  mean "checkpoint dtype", which is bf16 for Qwen2.5. `run.json` records `str(model.dtype)` read
  back after loading. A unit test saves the tiny model with a bf16 config and asserts that
  `from_pretrained(..., dtype="auto", device="cpu").model.dtype == torch.float32`.
- **Provenance in `run.json`**: `schema_version`, `git_sha`/`git_dirty` (from `git rev-parse HEAD`
  / `git status --porcelain`; the env var `LLM_EVAL_GIT_SHA` wins when set, e.g. in Docker; `null`
  when neither is available — this never fails a run), `config` (post-override, exactly as hashed),
  `config_hash`, `library_versions` (python, torch, transformers, tokenizers, datasets,
  huggingface_hub, numpy, pandas, pyarrow, scipy, statsmodels, llm_eval), per model
  `{provider, path, revision, dtype, device}` resolved, per task `{path, revision, split, n_rows,
  example_ids}`, `started_at`, `finished_at`, `failed_cells`, `summary` (§8.2).
  `model_revision` is obtained by `local = huggingface_hub.snapshot_download(path,
  revision=cfg.revision, allow_patterns=["*.json", "*.safetensors", "*.txt", "*.model", "*.jinja"])`
  (respects `HF_HUB_OFFLINE`), recording `Path(local).name` (the 40-hex commit) and loading weights
  and tokenizer **from `local`**, so the hash recorded is the hash used. `config._commit_hash` is
  absent in transformers 5 and is never used. An injected in-memory model records `None`.
- **Reruns** are grouped by `(config_hash, device, dtype)`.
- **Test–retest (README numbers, measured on Day 3 from the full-grid reruns)** — three numbers,
  reported separately and never conflated:
  (a) *Determinism*: fraction of (cell, example) pairs whose `prediction` is identical in **all 3**
  same-seed reruns on the same device (not the mean of pairwise agreements), split by provider ×
  scoring mode. Local log-likelihood cells are expected at 1.000 and serve as a correctness check;
  generation and API cells (temperature 0 is not deterministic at the providers) are the informative
  part. (b) *Exemplar-resampling stability*: with examples held fixed and `exemplar_seed ∈ {s0, s1, s2}`,
  per-example prediction agreement on `few_shot_3` cells, plus the per-cell max |acc_r − acc_r'|
  next to that cell's CI half-width. This is the robustness number the README one-liner quotes.
  (c) *Conclusion stability*: the fraction of significance-matrix verdicts (§7.7: significant or
  not, and direction) unchanged across the 3 reruns. Cross-device (MPS fp32 vs CUDA fp32) agreement,
  if measured, is labelled as such.

### 7.6 Statistics (Day 1: bootstrap CI; Day 4–5: the rest; designed now because the schema must support it)

- **Primary outcome.** Every per-example row carries `metric` and `primary_correct` (§8.2), set by
  `primary_metric(task_type, scoring)`: `correct_norm` for log-likelihood MC cells (`acc_norm`),
  `correct` for generation-mode MC cells (`acc`), `correct` for GSM8K (`exact_match`). All CIs,
  paired tests, matrices, variance decompositions and dashboard views read `primary_correct` and
  **never pool rows with different `metric`**. A comparison across modes is computed only on request
  and is labelled "cross-mode: prompt effect confounded with scoring method".
- **Complete cases and pairing.** Before any paired analysis, `stats.py` asserts that the cells
  share `task`, `dataset_revision`, `metric` and the same `example_ids` set (from `run.json`), then
  uses the examples with `status == "ok"` in every cell of the family. Every table and matrix cell
  prints `n` / `n_pairs`; excluded example ids are listed per cell.
- **Bootstrap CI** (`stats.py`, Day 1): one resample index matrix `idx[b, i]` (B=1000 × n) per
  task from `child_rng(seed, "bootstrap", task.name)`, shared by every cell of that task, so
  marginal CIs, paired-difference CIs, `P(rank = 1)` per cell (Day 4) and variance-share CIs
  (Day 5) are mutually consistent. Percentile interval of the mean of `primary_correct` (also
  reported for `acc` and `acc_norm`). Simulated coverage is 0.95 at n=100–300, so BCa is not
  offered. A unit test checks the interval against `statsmodels.stats.proportion.proportion_confint(
  method="wilson")` to within 0.02 at n ≥ 100. Intervals are displayed to one decimal in percentage
  points (the Monte Carlo SD of an endpoint at B=1000 is ≈0.5 pt).
- **Paired comparisons** (Day 4): on complete cases, build the 2×2 discordance table
  `(b = A right, B wrong; c = A wrong, B right)`. **Primary test**: McNemar exact
  (`statsmodels.stats.contingency_tables.mcnemar(table, exact=True)`, the two-sided binomial test on
  `b, c`); `b + c = 0` → `p = 1`. **Wilcoxon** is reported because the brief requires it, called as
  `scipy.stats.wilcoxon(d, zero_method="wilcox", correction=False, method="approx")`; on 0/1 data it
  is algebraically the uncorrected asymptotic McNemar statistic `z = (b − c)/√(b + c)` (so
  anti-conservative at small `b + c`), and a unit test asserts its p equals
  `mcnemar(table, exact=False, correction=False).pvalue` to 1e-9. **Effect size**: paired bootstrap
  CI of `acc_A − acc_B` from the shared index matrix. Any disagreement between the tests is flagged
  in the report, never resolved silently.
- **Multiple comparisons** (Day 4): one family per task = all one-factor contrasts: model pairs
  within each prompt variant (`V·C(M,2)`) plus prompt pairs within each model (`M·C(V,2)`); `k` is
  computed from the run's grid and printed under the matrix (k = 9 for 2 models × 3 variants, 30 for
  4 × 3). Pairs that differ in both factors are not in the confirmatory family; the dashboard still
  shows them, labelled "exploratory, uncorrected". The ★ marks Bonferroni-adjusted McNemar p < 0.05
  (as the brief specifies); the Holm-adjusted p (`statsmodels.stats.multitest.multipletests`) is a
  sensitivity column and is never less significant than Bonferroni.
- **Variance decomposition** (`variance.py`, Day 5), per task, on complete cases, within one
  scoring mode (HellaSwag headline = log-likelihood cells; the generation-mode run of §7.3 gives the
  three-variant decomposition): (1) *Headline*: the `M×V` matrix of cell accuracies decomposed into
  model main effect, prompt main effect and interaction as shares of the between-cell sum of
  squares, each with a 95% CI from the shared bootstrap index matrix (the same ids resampled in every
  cell). (2) *Supplementary*: a blocked OLS ANOVA
  `primary_correct ~ C(example_id) + C(model) * C(prompt_variant)` (`statsmodels.formula.api.ols` +
  `anova_lm`, type II, equal to type I because the design is balanced), reporting η² for example,
  model, prompt, interaction and residual. The item term is included because every cell scores the
  same examples (a crossed repeated-measures design); without it item difficulty lands in the
  residual and the factors appear to explain ≈2% of variance, which is correct and useless. Caveat
  stated in the report: a linear probability model on binary outcomes is descriptive; inference
  comes from the paired tests. Stretch goal: `BinomialBayesMixedGLM` with an example random intercept.
- **Power** (README protocol, Day 7): McNemar sample size `n = [z_{1−α/2}·√ψ + z_{1−β}·√(ψ − Δ²)]² / Δ²`
  (Connor 1987) with `ψ = p_b + p_c` the discordance rate, `α = 0.05/k`, 80% power. `ψ` is taken
  from the Day 2 sample-grid run (it needs at least two cells; the single-cell Day 1 run cannot
  provide it). The README reports the **minimum detectable effect** at the brief's fixed n=500/300
  (≈7 pts / ≈11 pts at k=9, ψ≈0.2–0.3) and the n each primary comparison would need for Δ=0.05
  (≈1,000 at ψ=0.2, k=9). Comparisons whose observed |Δ| is below the MDE are labelled
  "underpowered — no conclusion", never "no difference". The n is fixed by the brief; the README
  does not claim it is sufficient for Δ=0.05.

### 7.7 Decision rule (pre-specified)

1. Primary metric per task: HellaSwag `acc_norm` (log-likelihood cells; `acc` in the generation-mode
   prompt-effect run), GSM8K `exact_match`. HellaSwag `acc` is secondary.
2. Comparison family per task as in §7.6 (`k = V·C(M,2) + M·C(V,2)`); diagonal pairs are exploratory.
3. Verdict "A > B" iff the Bonferroni-corrected McNemar exact p < 0.05 **and** the paired-bootstrap
   95% CI of `acc_A − acc_B` excludes 0. Holm is a sensitivity column; Wilcoxon is shown and labelled
   "≡ uncorrected asymptotic McNemar on 0/1 data".
4. Any pair where the tests or the two corrections disagree is flagged in the report.
5. Named hypotheses, committed in the README "Experiment protocol" **before** the full-grid run
   (the commit sha is cited next to them): H1 `few_shot_3 > zero_shot` on GSM8K for Qwen2.5-0.5B;
   H2 `Llama-3.2-1B > Qwen2.5-0.5B` on HellaSwag `acc_norm` (zero-shot); H3 `cot > zero_shot` on
   GSM8K for Llama-3.2-1B.
6. The README leaderboard sentence is generated by `report.py` from the shared bootstrap: "A
   point-estimate leaderboard orders all K pairs per task; M survive the pre-specified paired test;
   the top-ranked cell is #1 in Z% of bootstrap resamples."

## 10. Testing strategy

- **Offline unit tests** (default `pytest`): config validation and `config_hash` (differs only in
  `output_dir` → equal; differs in `seed` → different); grid expansion and per-cell rejections;
  `seeding` determinism; HellaSwag preprocessing against hand-written literals including a
  `[substeps]` ending; nested deterministic subsets (n1 < n2 ⇒ ⊂, Python `int` elements, unique ids,

## 12. Decisions made by the author (not in the brief)

1. **Log-likelihood scoring for HellaSwag** with lm-eval preprocessing, tokenization and `acc_norm`:
   standard for base models this small, comparable to published numbers. Generation-mode MC exists
   for `cot`, API models and the forced prompt-effect run.
2. **McNemar exact is the primary paired test**; Wilcoxon is reported because the brief names it and
   is documented as the uncorrected asymptotic McNemar on 0/1 data; a paired bootstrap gives the
   effect size. The decision rule (§7.7) is written before the data exist.
3. **`seeding.child_rng` for every random draw**: independent, order-free streams; per-example
   exemplar draws so the example bootstrap covers exemplar variability.
4. **`float32` by default on every device**: correctness and cross-device comparability over speed
   at 0.5–1B scale (1.9 GB of weights); bf16 is opt-in.
5. **Row position at a pinned dataset revision as the native id** (HellaSwag `ind` is not unique);
   **nested subsets** via a seeded permutation.
6. **One parquet per run (long format) with an explicit pyarrow schema** that already carries the
   Day 2–3 columns; `status`/`parse_ok` separate infrastructure failures from model failures.
7. **One-factor contrast family** for the significance matrix (k=9 for the local grid); diagonal
   pairs are exploratory. The brief's Bonferroni drives the ★; Holm is a sensitivity column.
8. **Two HellaSwag analyses** (log-likelihood model comparison; generation-mode prompt-effect run)
   instead of one confounded grid.
9. **Item term in the ANOVA** and a cell-mean decomposition with bootstrap CIs as the headline.
10. **torch in a `local` extra** so the Streamlit Cloud install is torch-free; CPU torch index on Linux.
11. **uv + `uv.lock`**; `requirements*.txt` generated. **argparse** CLI. **Tiny random Llama** for
    adapter tests. **matplotlib** in a `report` extra for the README figure (flagged to the user).

| 16 GB unified memory (fp32 weights 1.9 GB; peak MPS ≈3.7 GB at bs 8, ≈7.7 GB over n=500; swap if other jobs run) | slice logits before `log_softmax`; one model process at a time; `torch.mps.empty_cache()` between cells |

## 15. As built, Days 2–7 (2026-10-23)

Days 2–7 were built efficiency-first against the brief; where the result differs from §1–14, the
code and this section win.

- **Scope re-aligned to the brief.** Kept: the two HellaSwag analyses (§7.3), McNemar exact as the
  verdict test with Wilcoxon reported (§7.6–7.7, pre-registered), one-factor comparison family,
  per-example exemplar draws, test–retest over three same-seed reruns. Dropped: rank
  probabilities and the generated leaderboard sentence, the forest plot and the matplotlib
  `report` extra's use, exemplar-seed stability runs (one exemplar seed), the
  `hellaswag_prompt_effects.yaml` name (its role is `configs/eval/local_gen.yaml`).
- **Configs.** `local_ll.yaml` (HellaSwag × zero/few-shot by log-likelihood),
  `local_gen.yaml` (both tasks × all three variants by generation), `api_gen.yaml` (the same grid
  for GPT-4o-mini and Claude Haiku 5.5), `sample_grid.yaml` (20-example check), `hypotheses.yaml`.
  Llama-3.2-1B comes from the ungated `unsloth/Llama-3.2-1B` mirror at a pinned revision.
- **Prompts** (§7.3) carry a one-line instruction (e.g. `Reply with one letter.`,
  `finish with "The answer is N."`) so one text works as a completion prompt for base models and
  as a user message for chat models; lettered blocks start with `Context:`. Generation budgets
  are 8 tokens for a multiple-choice letter and 256 otherwise (§7.2's 512 for CoT was cut after
  the 20-example benchmark); stop strings per (task type, variant), with few-shot GSM8K stopping at
  the blank line between exemplars.
- **GSM8K extraction** takes the *first* "answer is N" (base models keep writing after their
  answer), else the last number (§7.2 said the last "answer is").
- **Generation** (`HFCausalLM.generate`): left-padded, length-sorted batches, an explicit greedy
  `GenerationConfig` with neutral temperature/top-p so checkpoint sampling defaults (Llama's
  `do_sample: true`) never apply. Log-likelihood batches are capped at 1 GiB of fp32 logits.
- **API adapters** (`models/api_model.py`): one user message per prompt, concurrent requests,
  SDK retries, failures as `status="error"` rows. OpenAI: temperature 0 and a seed. Claude models
  accept only default sampling (and API version 2026-10-21 rejects sampling parameters on every
  model), so Anthropic calls send none and disable thinking; their reruns measure sampling noise.
- **Analysis** (`evaluation/analysis.py`, `analysis_report.py`, `variance.py`): as §7.6–7.7, with
  the minimum detectable effect computed at the observed discordance rate; test–retest reports
  agreement and conclusion stability (exemplar-resampling stability dropped with the exemplar-seed
  runs). `llm-eval analyze` writes `docs/results.md`, `docs/results.json` and the README block.
- **MLflow** (`tracking.py`): a local SQLite store, one MLflow run per run directory plus one for
  the analysis; `make mlflow`, `make mlflow-ui`.
- **Dashboard** (`serving/app.py` over `serving/dashboard.py`): a selectable cell table; two
  selected rows give the paired comparison and the disagreeing examples. Deployed per the hosting
  plan on Streamlit Community Cloud from `requirements.txt` (torch-free).
- **Runs** were made from a git worktree pinned to the commit that produced them, so code edits
  during the hours-long reruns could not leak into later runs; the Day-1 smoke run moved to
  `data/samples/smoke/`. A background grid on the 16 GB laptop was stopped for low memory, so the
  grid can also run on a cloud GPU: `scripts/modal_eval.py` (Modal; every finished run is saved to
  a volume at once) or `scripts/cloud_gpu_run.sh` (any SSH GPU machine). Reruns are grouped by
  config hash *and* hardware, as §7.5 specifies, and an analysis that mixes hardware for one
  config is rejected.
